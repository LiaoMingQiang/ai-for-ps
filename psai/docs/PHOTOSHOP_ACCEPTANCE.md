**这份清单里的每一条都还没有跑过。** 开发机上没有 Photoshop，
所以凡是需要真实 Photoshop 才能确认的行为，我都没有验证，只能靠人工过一遍。

下面先说清楚哪些是自动化真的测到了的，再列出剩下必须手工做的部分。

## 一、自动化已经覆盖的（可以信）

这些在 `npm test` 里每次都跑，改坏了会当场变红。

### 遮罩的极性、合成与判定 —— `packages/helper/test/mask.test.mjs`

**极性约定**（docs/RUNNINGHUB.md、PRD §7.5.2）：**透明处即为要处理的区域**。
ComfyUI 的 `LoadImage` 输出 MASK 时做的正是 `1 - alpha`。所以
`alpha = 255 - 选区灰度`：用户选中的地方变透明（处理区），
没选中的地方不透明（保留区）。

| 覆盖点 | 怎么测的 |
| --- | --- |
| **极性** | 断言选中处完全可编辑、未选中处完全保留。第一版正好写反了 |
| **极性（羽化方向）** | 沿半径采样，断言"可编辑程度"从圆心到圆外单调不增 |
| 生产路径：硬矩形 | 按 bounds 裁图 + 按**同一个** bounds 读遮罩，断言整块可编辑且**判为可用** |
| 生产路径：羽化圆形 | 裁完之后中心可编辑、四角保留、过渡带留存 |
| 不规则形状保真 | 对角线三角形逐像素比对，任何"退化成矩形"的实现都过不了 |
| 替换而非相乘 | 先造一张自带透明的图，再用全选中遮罩合成，断言整张变可编辑 |
| 尺寸不符报错 | 断言抛错且 `code` 与 `details` 正确，不做缩放对齐 |
| 没有可编辑区 → 不可用 | 唯一一种真正的失败：整张都是保留区，等于没圈任何东西 |
| 整张可编辑 → **可用** | 裁过的矩形选区、全选，都是合法用法，不该被拦 |
| alpha 的**出处** | 只有真的合成过选区灰度的资产才算"带了选区"；天然透明不算 |
| 走真实上传端点 | 上传后把资产取回来重新解码，逐点验极性 |

### 选区遮罩的读取 —— `packages/plugin/test/bridge-writeback.test.mjs`

| 覆盖点 | 怎么测的 |
| --- | --- |
| 用同一个 bounds | 断言 `getSelection` 收到的 `sourceBounds` 就是截图用的那个 |
| 单通道字节布局 | 棋盘图案逐点比对 |
| 多通道交错 | `components=4` 时按步长取第 0 通道，逐点比对 |
| 羽化 / 不规则原样带回 | 逐点比对，并断言中间值确实存在 |
| `imageData` 释放 | 断言 `dispose()` 被调用 |
| **接口报错 ≠ 版本老** | 断言提示里说的是"读取失败"并带上原始报错 |
| 数据长度不足 | 判为失败，不拿半截数据当遮罩 |
| 尺寸对不上 | 判为失败，说清两边分别多大 |
| 真的没有接口 | 这一种才提示"版本" |

### 桥的判断逻辑 —— `packages/plugin/test/bridge-writeback.test.mjs`

用一个可控的假 `photoshop` 模块驱动**真实的桥代码**，图层树和返回值由用例摆布。

| 覆盖点 | 怎么测的 |
| --- | --- |

| 同名图层去重 | 断言上一次写进去的同名图层被先删掉 |
| 删不掉时不判失败 | 锁定图层删不掉，写回照常进行 |
| assetOnly 两种措辞 | 断言"按设置"和"没有可写的文档"给的是不同的话 |

确认测试确实变红（遮罩 5 条、桥 5 条）。测不出问题的测试等于没写。

| # | 步骤 | 期望 | 结果 |
| --- | --- | --- | --- |

> **关于 B3：全选是合法的，不该被拦。**
>
> 早先这份清单要求"全选必须被拦下"，而实现里明确写着"整张都可编辑是合法的"——
> 两边对不上。对的是实现：遮罩是**按选区外接矩形裁过之后**才判定的，
> 所以一个普通的矩形选框裁完同样是"整张都可编辑"。
> 把这种拦掉，等于把最常见的矩形选区一起拦掉。
>
> 代价是全选（Ctrl+A）确实会走下去，让模型重绘整张图。那是用户明确
> 表达的意思，不是误操作 —— 我们分不出、也不该替他分辨。

## 三、已知的、尚未验证的假设

这些是实现时按文档和惯例写的，**没有在真机上确认过**：

1. **`imaging.getSelection` 的返回布局** —— 假设 chunky（交错）排布，
   按 `components` 跨步取第 0 个通道。代码现在会逐项核对
   `components` / `componentSize` / `colorSpace` / 返回窗口，
   任何一项对不上就**放弃遮罩**并说明原因，不猜。
   所以布局假设错了的表现是"退回外接矩形并有提示"，不是错位合成 ——
   但 A1–A6 仍会整片达不到预期。
2. **`componentSize` 与 `getData` 的返回类型是否一致** —— 假设
   8 位给 `Uint8Array`、16 位给 `Uint16Array`、32 位给 `Float32Array`，
   并据此换算值域。不一致时会判失败而不是产出乱码遮罩。A10/A11 专验这个。
3. **`getSelection` 认不认 `componentSize: 8` / `colorSpace: 'Grayscale'`**
   —— 我们会显式传这两个，但不依赖它们生效（照样逐项核对拿到的东西）。
   老版本忽略它们是预期内的。
4. **`sourceBounds` 的语义** —— 假设它按选区外接矩形裁剪，
   且返回尺寸与我们 crop 出来的画面一致。不一致时代码会**放弃遮罩**
   （退回矩形）而不是错位合成 —— 这是有意的保守选择，但意味着 A2/A3
   可能"没报错但也没生效"。检查 A2 时要真的去看 alpha，别只看有没有报错。
5. **合并后图层的 `bounds`** —— 用它判断"有没有像素"（零面积 = 空）。
   一开始写的是查直方图，但那条判据会误伤纯黑图层（阴影层、蒙版底都是
   常见用法，所有像素都落在 0 号桶）。已经换成 bounds 并加了回归用例，
   不过"Photoshop 给的 bounds 在合并之后是不是及时更新的"仍未在真机确认。
   C3 和 C6 一起看。
6. **`layer.delete()`** —— 假设 UXP 的图层对象有这个方法。
   没有的话去重会静默失效（我们吞掉了异常），D4 会看到图层堆叠。
7. **`placeEvent` / `paste` 空转时 `activeLayers` 的样子** —— 我们靠
   "置入前后的图层 id 集合"判断有没有真的新建。假设 Photoshop 在
   置入成功时一定把新图层设为当前图层。假设不成立的话，表现是
   写回报"没有新建图层"而其实建了 —— 保守方向，但 D1/D2 会失败。
8. **图层名的长度上限** —— 出处标记会让名字变长（`[psai:…@…]`）。
   写完会读回来核对，写不全就判失败并回滚，所以不会产出认不全的标记；
   但如果上限比预计的紧，D9 会看到写回一直失败。
9. **UXP 数据目录的可写性** —— 待报队列落在那里。写不进去时会退回
   只在内存里（本次会话仍然重试），F7 会失败。

第 1、2 条最需要留意：`imaging.getSelection` 的数据布局要是和假设不符，
A 组会整片失败，而且失败的样子多半是"没报错但遮罩没生效"——
所以 A2、A3 一定要真的去看 alpha，别只看有没有弹错误。
